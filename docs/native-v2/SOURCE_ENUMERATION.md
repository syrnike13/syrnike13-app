# Windows source enumeration

`SourceRegistry` is the native-v2 boundary for discovering active Windows monitors and meaningful top-level windows. It accepts a `SourceEnumerator` platform adapter and returns bounded value snapshots; public snapshots never contain `HWND`, `HMONITOR`, device paths, process creation times, or another platform key.

## Identity contract

Every registry instance assigns a process-local opaque `src_…` ID to one continuously observed platform-object lifetime. A title, label, minimized state, or process-path update preserves that ID. Once a source is absent from a successful reconciliation its entry is removed, and a later candidate receives a fresh ID even when its private adapter key is identical; IDs are monotonic within a randomized registry namespace and are never parsed back into Win32 handles.

Monitor identity always uses the active DisplayConfig adapter LUID plus target ID. The optional `monitorDevicePath` and friendly device name are metadata only, so a path appearing or disappearing across successful queries cannot switch a live monitor between identity namespaces. DisplayConfig sizing/query is retried at most three times during topology races. The canonical GDI-name-to-target mapping is queried both before and after `EnumDisplayMonitors`; any mapping transition, query failure, `GetMonitorInfoW` failure, or unmatched GDI monitor fails the batch and preserves prior registry state. Friendly labels and enumeration order never define identity, so two identical monitor models remain separate.

Window identity combines the current `HWND`, PID, process creation time, owner TID, window class, and a process-local WinEvent lifetime epoch. One joinable event-pump thread records `EVENT_OBJECT_CREATE`/`EVENT_OBJECT_DESTROY`; a pre-scan barrier and two post-scan barriers bracket two epoch/fingerprint validations, so ordinary delayed close/recycle cannot escape between a drain and validation. The hook routes through weak/shared event state rather than an asynchronous raw owner pointer. Proven-dead HWND epochs are pruned after each event drain and at capacity, while epochs unseen only because of truncation remain intact; if 512 live/uncertain lifetimes still fill the tracker, the batch fails without rotating live IDs. Hook failure or a missed barrier likewise preserves prior registry state. WinEvent remains best-effort Windows infrastructure: a protected desktop could suppress lifetime events and recycle the complete same-process/same-thread fingerprint between successful calls, so this Windows ambiguity is explicit and no code claims that `HWND` alone proves identity.

## Snapshot metadata, selection, and limits

Every returned source has `availability`, `flags.available`, and `captureSupport`. Enumerated objects are currently `available`; disappearance is reported as a removal in reconciliation diff rather than a stale unavailable object. `captureSupport` is `unknown`, because enumeration cannot prove WGC/DXGI or protected-content capturability without opening a forbidden capture session. An exclusion describes selection quality and does not invent capture support.

Monitor snapshots always contain logical desktop bounds from `MONITORINFO`. `physicalBounds` comes from the current documented `DEVMODE` output mode and is `null` when Windows does not provide a consistent current mode. `dpi.x`/`dpi.y` are raw panel DPI from `GetDpiForMonitor(MDT_RAW_DPI)`, while `dpi.scale` is the effective discrete desktop scale from `GetScaleFactorForMonitor`; each is independently `null` on API failure, so the snapshot never substitutes 96 DPI or `1.0` as invented precision. Primary, bounds, DPI, and scale are mutable metadata and never participate in identity.

The Win32 adapter uses only bounded, non-message enrichment: `EnumWindows`, `GetWindowThreadProcessId`, visibility/iconic/root checks, `GetWindowRect`, `GetClassNameW`, caption `GetWindowTextW`, `DwmGetWindowAttribute(DWMWA_CLOAKED)`, and limited process queries. It never sends `WM_GETTEXT`, `WM_GETICON`, or a synchronous cross-process message, so a hung UI thread cannot stall enumeration. One `EnumWindows` pass classifies each observed HWND at one visibility point, retaining bounded visible and hidden sets separately before visible-first selection; a mid-scan visibility flip therefore cannot fall between passes and remove a live ID. Titled hidden, cloaked, and invalid-bounds windows remain in the snapshot with `not_visible`, `cloaked`, or `invalid_bounds`; protected/capture state remains typed `unknown`. Untitled and non-root candidates produce bounded typed omission diagnostics. Own-process windows produce `window_omitted_own_process` by default; `--include-own-windows` is a fixture-only override that returns them with `flags.ownProcess=true` and the `own_process` exclusion. Window `label` is the bounded executable basename selected from the wide process path before UTF-8 conversion, never a copy of title; it is empty with `window_process_metadata_unavailable` when process metadata is inaccessible.

One registry permits one enumeration in flight. A concurrent request returns typed incomplete failure instead of queuing, while `shutdown()` atomically cancels adapter callbacks/barrier waits and prevents later enumeration or resolve validation. Each kind has explicit complete/partial/failed status internally: partial or truncated batches preserve unseen live entries, while only a complete batch may emit typed removed IDs. A snapshot contains at most 8 monitors and 256 windows plus at most 64 diagnostics and eight exclusions per source; active state is capped at 16 monitors/512 windows, and the removed-ID FIFO retains 512 tombstones. Titles, labels, source IDs, and diagnostic code/detail values are at most 256 valid UTF-8 bytes. The temporary process-image query is capped at 32,768 wide characters; only its bounded basename crosses the adapter boundary.

## Probe and fixture

`media_probe enumerate-sources` writes one JSON document to stdout; failures and usage errors go to stderr. It accepts `--kind monitor|window|all`, strict decimal `--repeat N` for `1..1000`, `--diff`, `--sanitized`, and the fixture-only `--include-own-windows`. Repeats retain one registry and diff exact added/updated/removed opaque IDs. `--sanitized` emits only counts, status, diagnostic codes, and resource measurements, so CI artifacts contain no window title or process metadata. A separate warm registry absorbs process-wide Windows lazy initialization; the measured registry is then created and destroyed inside the resource interval. The enforced budget is at most two additional handles and zero additional threads.

```powershell
pnpm --filter @syrnike13/windows-media-engine build
pnpm --filter @syrnike13/windows-media-engine test
pnpm --filter @syrnike13/windows-media-engine probe:sources
pnpm --filter @syrnike13/windows-media-engine probe:sources:sanitized
```

`source_window_fixture.exe` is built only as a native test executable. Its pipe protocol drives title changes, a second window, minimize/restore, hide/show, a deliberately blocked UI thread, rapid destroy/create, and destroy/reconcile/create without sleeps or retry loops; `source_win32_integration_tests.exe` observes every transition through the public registry API. Hung-window enumeration has a 500 ms wall-clock assertion, and CTest terminates the whole integration executable after 10 seconds if cleanup regresses.
