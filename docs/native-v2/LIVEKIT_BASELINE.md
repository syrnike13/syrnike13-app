# Native v2 LiveKit baseline

The project uses release `v1.10.0-syrnike.1` from the standalone `syrnike13/client-sdk-cpp` fork at commit `c4848874cc9a316b319979f17a0b6944e50e6246`, based on upstream v1.10.0 commit `336d14e17d9432acce89e4c0d57078bbfbb23026`. The fork adds deterministic Room/E2EE callback teardown needed for repeated in-process Room lifecycles. Its pinned Windows archive SHA-256 is `5e0180c02111e22264337286732d426b07cf460f724cb1e99e72f02a07fc2c48`; CMake rejects any other archive and has no local SDK override. The neutral observer uses `@livekit/rtc-node@0.13.34`, token fixtures use `livekit-server-sdk@2.18.0`, and local Docker keeps the recorded v1.13.6 image digest.

`pnpm native-media:lab` first drives a real Room from `MediaRuntimeSupervisor` through the Electron utility, addon, Engine, and production `LiveKitRoomTransport`, then verifies connected/off snapshots and graceful shutdown. The publisher uses the same Engine/RoomOwner path to publish deterministic BGRA video and 48 kHz mono PCM through public SDK APIs, and a separate Node observer validates reception. The lab accepts Docker locally or `MEDIA_LAB_SERVER_EXE`; Windows CI builds the repository LiveKit server and uploads `packages/native-media-lab/artifacts/latest-report.json`.

The C++ SDK exposes synchronous Room operations, so the adapter owns one persistent operation lane and one persistent cancellation lane. `RoomOwner` independently bounds connect at 12 seconds and disconnect/cancellation at 2 seconds; a missed deadline makes the utility epoch fatal and the supervisor replaces its process. A successful SDK connect is committed only after the actual Room name and local participant identity match the desired authority. Generation-fenced completion returns through the bounded mailbox, LiveKit global runtime is utility-process scoped, Room and tracks are connection scoped, and each credential lease is consumed by one attempt.

The scenarios cover normal audio/video, actual slow-observer processing, late join, republish, disconnect before publication, participant failure, cancellation/late completion, and fifty connect/publish/unpublish/disconnect cycles inside one SDK/Engine process. In-process churn records Windows thread/handle deltas and the transport's outstanding operation/callback count after a track/cancellation warm-up; every cycle must return to zero pending callbacks, with no thread growth and no more than two additional handles. Publisher cleanup returns normally after Engine shutdown and `livekit::shutdown()`; `_Exit` is not used.

Phase A uses CPU-backed synthetic buffers. WGC, DXGI, WASAPI, Media Foundation, D3D11, cameras, microphones, and hardware encoders remain out of scope.
