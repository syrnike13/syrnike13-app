# Native v2 LiveKit baseline

The project uses release `v1.10.0-syrnike.2` from the standalone `syrnike13/client-sdk-cpp` fork at commit `f1b3d160300c4fb2043cdff455d234e1b3ec3915`, based on upstream v1.10.0 commit `336d14e17d9432acce89e4c0d57078bbfbb23026`. The fork retains the deterministic Room/E2EE callback teardown from `.1` and adds publisher-transceiver reuse for repeated local publication. Its pinned Windows archive SHA-256 is `caab37d69516fd7b9da146bb80574e3b2bc1d0e422b2ad5f8e1a2dceea91bcf8`; CMake rejects any other archive and has no local SDK override. The neutral observer uses `@livekit/rtc-node@0.13.34`, token fixtures use `livekit-server-sdk@2.18.0`, and local Docker keeps the recorded v1.13.6 image digest.

`pnpm native-media:lab` first drives a real Room from `MediaRuntimeSupervisor` through the Electron utility, addon, Engine, and production `LiveKitRoomTransport`, then verifies connected/off snapshots and graceful shutdown. The publisher uses the same Engine/RoomOwner path to publish deterministic BGRA video and 48 kHz mono PCM through public SDK APIs, and a separate Node observer validates reception. The lab accepts Docker locally or `MEDIA_LAB_SERVER_EXE`; Windows CI builds the repository LiveKit server and uploads `packages/native-media-lab/artifacts/latest-report.json`.

The C++ SDK exposes synchronous Room operations, so the adapter owns one persistent operation lane and one persistent cancellation lane. `RoomOwner` independently bounds connect at 12 seconds and disconnect/cancellation at 2 seconds; a missed deadline makes the utility epoch fatal and the supervisor replaces its process. A successful SDK connect is committed only after the actual Room name and local participant identity match the desired authority. Generation-fenced completion returns through the bounded mailbox, LiveKit global runtime is utility-process scoped, Room and tracks are connection scoped, and each credential lease is consumed by one attempt.

The scenarios cover normal audio/video, actual slow-observer processing, late join, republish, disconnect before publication, participant failure, cancellation/late completion, and fifty connect/publish/unpublish/disconnect cycles inside one SDK/Engine process. In-process churn records Windows thread/handle deltas and the transport's outstanding operation/callback count after a track/cancellation warm-up; every cycle must return to zero pending callbacks, with no thread growth and no more than two additional handles. The screen oracle separately exercises 30 publish/unpublish cycles and records a resource sample after every acknowledged unpublish. Publisher cleanup returns normally after Engine shutdown and `livekit::shutdown()`; `_Exit` is not used.

The `.2` reuse pool is scoped to one `RtcSession` and is dropped with that session. A removed sender is eligible only when media kind and ordered RID list match; current encoding parameters are restored before the track and `sendonly` direction are reattached, and a failed restore stops the candidate and allocates a fresh transceiver. This policy fixes the demonstrated same-profile screen churn, but it is not proof for camera/screen transitions, codec-preference changes, simulcast/scalability changes, hardware encoder backends, E2EE, reconnect, or partial restore failure. Those cases remain explicit gates for the production screen path; see [ADR 0008](../adr/0008-livekit-publisher-transceiver-reuse.md).

Phase A uses CPU-backed synthetic buffers, and Phase B adds WGC/D3D11 plus a CPU reference screen publisher. WASAPI, Media Foundation, cameras, microphones, and hardware encoders remain out of scope until their later phases.
