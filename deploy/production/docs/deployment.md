# syrnike13 Deployment

This directory contains the production Docker Compose based syrnike13 chat stack.

The deploy keeps runtime state on the server. GitHub Actions uploads repository files, but it does not overwrite:

- `data/`
- `.env`
- `.env.web`
- `secrets.env`
- `Syrnike.toml`
- `livekit.yml`
- `compose.override.yml`

Those files contain server-local state, generated config, or secrets.

## Required Server State

Use Ubuntu with Docker Engine and the Docker Compose plugin installed.

Open these ports:

- `80/tcp`
- `443/tcp`
- `7881/tcp`
- `50000-50100/udp`

If syrnike13 is behind an external reverse proxy, expose Caddy on `8880` through `compose.override.yml` generated by `generate_config.sh`, and proxy WebSocket paths `/ws` and `/livekit` correctly.

## GitHub Settings

Create the `production` environment in the `syrnike13/syrnike13-app` repository, then set:

Secrets:

- `DEPLOY_HOST`: server hostname or IP.
- `DEPLOY_USER`: SSH user.
- `DEPLOY_PATH`: absolute deploy directory, for example `/opt/syrnike13`.
- `SSH_PRIVATE_KEY`: private key allowed to SSH into the server.

Variables:

- `SYRNIKE_DOMAIN`: landing domain. Use `syrnike13.ru` for production.
- `SYRNIKE_APP_DOMAIN`: application domain. Use `app.syrnike13.ru` for production.
- `SYRNIKE_REVERSE_PROXY`: `false` for built-in Caddy on ports 80/443, `true` when another reverse proxy is in front.
- `SYRNIKE_VIDEO_ENABLED`: `true` to enable camera and screen sharing, `false` to disable.

## DNS

Create A/AAAA records for both hostnames and point them at the deployment
server before enabling the app host in Caddy:

- `syrnike13.ru` — landing site.
- `app.syrnike13.ru` — web application, invites and deep links.

Nightly uses `beta.syrnike13.ru` for the landing and `app.beta.syrnike13.ru` for
the application.

Channel Activities need wildcard records `*.activities.syrnike13.ru` and
`*.activities.beta.syrnike13.ru` pointing at the same server (see
[Channel Activities](#channel-activities)).

## Existing Hosts

On an existing server, update the server-local `Syrnike.toml` before the first
deploy with the app domain:

```toml
[hosts]
app = "https://app.syrnike13.ru"
```

Otherwise email verification and password-reset links keep pointing at the
landing domain; Caddy redirects them, but the canonical app origin should be
the app host.

## First Deploy

The first deploy generates server-local config by running:

```bash
./generate_config.sh "$SYRNIKE_DOMAIN"
```

The script answers the interactive reverse-proxy and video prompts from `SYRNIKE_REVERSE_PROXY` and `SYRNIKE_VIDEO_ENABLED`.

Back up `secrets.env` after the first successful deploy. Losing it can make existing uploaded files inaccessible.

## Updating Backend Services

Production images and deploys come from a manual run of
`.github/workflows/release-images-and-deploy.yml` on `main`. Nothing runs on
push: choose the workflow in the Actions tab, press **Run workflow**, type the
release version (for example `0.8.0`), and leave `services` empty for all app
services. The form also controls whether the deploy step runs and whether the
stable desktop release is published.

The typed version is used for the image tags, the application version baked into
the web and admin builds, the backend `VERSION` file, and the desktop release.
The repository `VERSION` file is not read by this workflow, so no commit is
needed to release.

Selecting the backend services only (for example
`services: api events autumn january gifbox activity-proxy crond pushd voice-ingress`) runs:

```bash
DEPLOY_SERVICES="api events autumn january gifbox activity-proxy crond pushd voice-ingress" ./scripts/deploy-on-server.sh
```

The server pulls the listed images and updates them through
`scripts/rollout.sh`:

- User-facing services (`api`, `events`, `autumn`, `january`, `gifbox`,
  `activity-proxy`, `voice-ingress`, `landing`, `web`, `admin`) are rolled out. When the image or compose
  definition changed, a second container starts next to the running one; once
  it accepts connections on its port the old container is stopped. Caddy
  reaches these services through network aliases (`syrnike13-<service>`) that
  both containers share and retries requests that hit a stopping container, so
  clients see no errors. A service whose image and definition are unchanged is
  left running.
- `events` hands its gateway clients over while it stops: it stops accepting
  connections, asks each client to reconnect (spread over 10 seconds), and
  exits once the clients moved, within its 45 second `stop_grace_period`.
  Clients open the new connection before closing the old one, so no events are
  lost. Each gateway process keeps its own presence region and only clears the
  regions of processes that are gone, starting 60 seconds after boot.
- Other services (`crond`, `pushd`, `livekit`, infrastructure) are recreated
  by `docker compose up -d --no-deps` only when they changed.

Rolled services must not set `container_name` or publish host ports, because
two containers run side by side during an update. They must also open their
port only once they can serve requests: readiness is checked by connecting to
that port. Every rolled service does so today (each binds after connecting to
its database and broker, web and admin after archiving their assets); a
service that binds earlier needs a readiness check before it is rolled. A new container that exits
or does not accept connections within `ROLLOUT_READY_TIMEOUT` (180 seconds)
is removed and the deploy fails with the old container still serving.

A manual `docker compose up -d <service>` still recreates the container in
place and causes a short interruption; use the deploy script instead.

## Updating The Full Stack

Run the production workflow manually with an empty `services` input when
production infrastructure files changed and the entire stack should be
reconciled.

Without `DEPLOY_SERVICES`, the server pulls every image, creates missing
services and removes orphans without touching running containers
(`docker compose up -d --no-recreate --remove-orphans`), then updates every
service the same way as above.

## Updating LiveKit

A LiveKit restart drops every room on the node. The LiveKit image is tagged
with the git tree of `services/livekit-server` (`tree-<hash>`); a release
reuses the existing image when that tree is unchanged, so `:latest` keeps its
digest and the container is not recreated. Only a change under
`services/livekit-server` publishes a new image and restarts LiveKit, so
schedule such releases for a quiet time, or run two LiveKit nodes.

### Two LiveKit nodes

With the `livekit-b` compose profile a second LiveKit node runs next to
`livekit`. Both share Redis, keys and webhooks; any node accepts signalling
and routes a participant to the node of its room. A LiveKit update then drains
one node at a time: SIGTERM makes the node take no new rooms while its rooms
stay up until they empty. After `LIVEKIT_DRAIN_TIMEOUT` (default 900 seconds)
a second SIGTERM closes the rooms still open and unregisters the node, so
their clients reconnect to the other node right away. Voice channels that are never empty therefore
see one reconnect per node update; all other rooms see none.

The second node needs its own host ports. Defaults:

| | TCP (ICE) | TURN UDP | TURN relay UDP | RTC UDP |
| --- | --- | --- | --- | --- |
| production `livekit-b` | 7883 | 3480 | 30201-30300 | 50201-50300 |
| nightly `livekit-b` | 7884 | 3481 | 30301-30400 | 50301-50400 |

To enable it:

1. Open these ports in the host and provider firewalls. Calls whose room lands
   on a node with blocked ports fail to connect media.
2. Add `COMPOSE_PROFILES=livekit-b` to the server-local `.env`. Override any
   port there with `LIVEKIT_B_TCP_PORT`, `LIVEKIT_B_TURN_UDP_PORT`,
   `LIVEKIT_B_TURN_RELAY_RANGE_START`/`_END` or
   `LIVEKIT_B_RTC_PORT_RANGE_START`/`_END`.
3. Run a full-stack deploy. The deploy script writes `livekit-b.yml` from
   `livekit.yml` with the second node's ports on every run, so edit only
   `livekit.yml`. It refuses to write it when `livekit.yml` sets
   `rtc.udp_port`, since both nodes would then share that port.
4. Check that both nodes are registered (`redis-cli HLEN nodes` in the
   project's Redis) and join a call on each node.

The first node keeps its compose definition, so enabling the profile does not
restart it. Each node uses roughly as much CPU and memory as its rooms need;
see `server-sizing.md`.

## Updating The Shared Edge

Production and nightly share the production Caddy container. Both deploy
workflows upload a candidate `Caddyfile` and run
`scripts/reload-caddy.sh`, which validates the candidate before copying it over
the bind-mounted file and applies it with `caddy reload`. The reload is locked
across both workflows and rolls the file back if Caddy rejects the new
configuration, so an edge update does not restart the container or disconnect
existing WebSocket and LiveKit sessions.

## Channel Activities

Every Activity Origin (`https://{id}.activities.syrnike13.ru`, nightly
`https://{id}.activities.beta.syrnike13.ru`) is served by the `activity-proxy`
service (ADR-0011, `services/backend/crates/services/activity-proxy`). Each
environment runs its own proxy against its own registry
(`activity_applications` in its MongoDB).

The proxy takes the application id from the `Host` header, looks the
application up (cached for 15 seconds, so disabling an application takes
effect within that time), and forwards the request to `origin_url`, or to the
matching `url_mappings` target for `/.proxy/{prefix}/…`, including WebSocket
upgrades. It never forwards `Forwarded`, `X-Forwarded-*`, `X-Real-IP` or other
client address headers, removes `X-Frame-Options`, and adds
`Content-Security-Policy: frame-ancestors <client origins>; connect-src 'self' wss://{id}.…`
next to the application's own policy. Unknown or disabled applications get
`404`.

Configuration (environment variables in `compose.yml`):

| Variable | Production | Nightly |
| --- | --- | --- |
| `SYRNIKE__HOSTS__ACTIVITIES` (also on `api` and `events`, which build `activity_url`) | `https://{id}.activities.syrnike13.ru` | `https://{id}.activities.beta.syrnike13.ru` |
| `SYRNIKE__ACTIVITIES__CLIENT_ORIGINS` (space separated, CSP `frame-ancestors`) | `https://app.syrnike13.ru http://127.0.0.1:*` | `https://app.beta.syrnike13.ru http://127.0.0.1:*` |
| `SYRNIKE__ACTIVITIES__ASK_DELEGATE_SUFFIX` | `.activities.beta.syrnike13.ru` | empty |
| `SYRNIKE__ACTIVITIES__ASK_DELEGATE_URL` | `http://caddy:14700/_caddy/ask` | empty |

`http://127.0.0.1:*` admits the desktop renderer, which the Electron app
serves from a random local port. `activities.proxy_listen` defaults to
`0.0.0.0:14707`.

The first-party Activity Lab is built into the web image and served by the
`web` service at `/_activities/lab/`; its registry entry uses
`origin_url = "http://web:5000/_activities/lab"`. The production proxy is
therefore only on the production default network, where `web` is the
production web service.

### Certificates

Caddy serves `*.activities.syrnike13.ru` and `*.activities.beta.syrnike13.ru`
with on-demand certificates (one Let's Encrypt certificate per application
host, issued on the first TLS handshake). Before issuing, Caddy asks
`http://syrnike13-activity-proxy:14707/_caddy/ask?domain=<host>` (global
`on_demand_tls` option):

1. A host under the production suffix is approved only if the production
   registry has that application enabled.
2. A host under `ASK_DELEGATE_SUFFIX` is forwarded to `ASK_DELEGATE_URL`.
   That is Caddy's internal `:14700` site (not published on the host), which
   passes the question to the nightly proxy over the edge network; the nightly
   proxy answers from the nightly registry.
3. Everything else is refused, so random subdomains cannot exhaust certificate
   rate limits.

`/_caddy/ask` and `/_health` are answered only for requests whose `Host` is not
an Activity Origin, so applications cannot shadow them. Until the production
proxy runs, Caddy refuses every activity certificate; existing hosts are not
affected.

### Local development

The defaults in `crates/core/config/Syrnike.toml` serve
`http://{id}.activities.localhost:14707` (browsers resolve `*.localhost` to the
loopback address) and allow `http://localhost:3001` and `http://127.0.0.1:3001`
to frame activities:

```bash
cargo run --manifest-path services/backend/Cargo.toml -p syrnike-activity-proxy
curl -H 'Host: lab.activities.localhost:14707' http://127.0.0.1:14707/
```

Register an application (enabled, with an `origin_url` such as the Vite dev
server of `apps/activity-lab`) in the local MongoDB first.

## Desktop Auto-Updates

Desktop installers and `electron-updater` manifests are served as static files from:

- URL: `https://<domain>/downloads/desktop/`
- Server path: `<DEPLOY_PATH>/data/desktop/`

Caddy serves that directory read-only from `data/desktop`. The directory is server-local state and is not overwritten by production deploy tar uploads.

Publishing flow:

1. Run `.github/workflows/release-images-and-deploy.yml` on `main` with the release version typed into the form and `desktop` enabled.
2. GitHub Actions builds Windows, macOS, and Linux packages.
3. The workflow publishes the desktop packages to the public GitHub Release, then sends only release metadata and `tooling/scripts/publish-desktop-release.py` to the production server. The server needs `curl`, Python 3, and PyYAML (`python3-yaml` on Ubuntu); GitHub credentials are not sent to it.
4. The server downloads packages over HTTPS into a private staging directory inside `data/desktop/`. It verifies GitHub's SHA-256 digests and manifest SHA-512 hashes and sizes, reusing already-verified packages on retries. Original Windows filenames with spaces are preserved even though GitHub normalizes release asset names.
5. Only after all packages pass verification does the publisher atomically replace package files and stable aliases, then publish `latest*.yml` last. A failed download leaves the previous public feed unchanged. Old release history is pruned only after successful publication.
6. Packaged desktop clients check `https://syrnike13.ru/downloads/desktop/` for updates.

The publication lock prevents concurrent publishers. Run publisher regression checks with:

```bash
python3 tooling/scripts/test_publish_desktop_release.py
```

To retry an already-published stable desktop release from a machine with GitHub CLI access, copy the publisher to the server and pipe `gh api repos/syrnike13/syrnike13-app/releases/tags/v<VERSION>` into `python3 <publisher-path> <DEPLOY_PATH>/data/desktop <VERSION>` over SSH. Do not upload new manifests separately or resume the old bulk SSH upload alongside the publisher.

Before the first desktop release upload, deploy production once so Caddy picks up the `/downloads/desktop/*` route and the `data/desktop` volume mount:

```bash
docker compose up -d --no-deps caddy
```

Health check:

```bash
curl -fsS "https://syrnike13.ru/downloads/desktop/latest.yml"
```

GitHub Releases remain available for manual downloads. Auto-update uses the production static feed.

## Stable Landing Download Aliases

The landing page links to stable URLs that always point at the latest desktop release:

- `https://<domain>/downloads/syrnike13-setup.exe`

Health checks:

```bash
curl -fsSI "https://syrnike13.ru/downloads/syrnike13.dmg" | head -5
curl -fsSI "https://syrnike13.ru/" | head -5
curl -fsSI "https://app.syrnike13.ru/" | head -5
```

## Android App

The Android app installs from the site, not from a store, and has no nightly
variant. Its files live in `<DEPLOY_PATH>/data/mobile/` (server-local, like
`data/desktop`), served read-only by Caddy:

- `https://<domain>/downloads/syrnike13.apk`: copy of the newest APK for the landing page.
- `https://<domain>/downloads/mobile/latest.json`: release feed; installed apps offer to update when its `versionCode` is newer.
- `https://<domain>/downloads/mobile/syrnike13-<VERSION>.apk`: versioned APKs (the newest `MOBILE_APK_KEEP_VERSIONS`, default 3).
- `https://<domain>/downloads/mobile/manifest`: Expo Updates (protocol v1) endpoint. Caddy serves `updates/<runtime>/manifest.json` for the app's `Expo-Runtime-Version` header, or `204` when that runtime has no update. Update files sit under `assets/` by content hash and never change.

Run `.github/workflows/mobile-release.yml` on `main`:

- `apk` with a version builds a signed APK (native changes, new permissions) and publishes it with the feed.
- `ota` publishes the current JS for installed APKs whose native fingerprint matches; no version is needed.

The APK is signed with the upload keystore from the `production` environment
secrets `ANDROID_UPLOAD_KEYSTORE_BASE64`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`,
`ANDROID_UPLOAD_KEY_ALIAS` and `ANDROID_UPLOAD_KEY_PASSWORD`. Every APK must use
the same key: Android refuses to update an app signed with another one, so a
lost keystore means every user reinstalls. Keep an offline backup.

Before the first mobile release, deploy production once so Caddy picks up the
`/downloads/mobile/*` routes and the `data/mobile` volume mount.

Health check:

```bash
curl -fsS "https://syrnike13.ru/downloads/mobile/latest.json"
```

## Nightly Channel

The `develop` branch publishes and deploys the independent nightly environment
from a manual run of `.github/workflows/nightly-release-and-deploy.yml`. A push
to `develop` starts nothing; run the workflow from `develop` when you want a
nightly build. The nightly version is the UTC build date plus the commit SHA
(`<YYYY.M.D>-nightly.<sha>`) and does not read the `VERSION` file. The `deploy`
input controls whether the run deploys after publishing images.

- Landing URL: `https://beta.syrnike13.ru`
- Application URL: `https://app.beta.syrnike13.ru`
- Server path: `/opt/syrnike13-nightly`
- Compose project: `syrnike13-nightly`
- Docker tags: `nightly` and `nightly-<sha>`
- Desktop delivery: GitHub prerelease `nightly`; no auto-update feed.

Production Caddy remains the edge proxy for both domains. It joins the shared
external Docker network `syrnike13-edge` and routes `beta.syrnike13.ru`
to the nightly landing and `app.beta.syrnike13.ru` to the nightly web app.
API and media stay on `beta.syrnike13.ru`. Nightly Activity Origins
(`*.activities.beta.syrnike13.ru`) go to the nightly `activity-proxy`.

Nightly keeps its own server-local runtime files and data:

- `data/`
- `.env`
- `.env.web`
- `secrets.env`
- `Syrnike.toml`
- `livekit.yml`
- `compose.override.yml`

Nightly LiveKit uses separate host ports to avoid conflicts with production:

- `7882/tcp`
- `3479/udp`
- `30101-30200/udp`
- `50101-50200/udp`
